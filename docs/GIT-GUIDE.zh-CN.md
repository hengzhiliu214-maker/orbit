# 中文 Git 协作速查

> 写给项目主人：以后想自己往这个仓库里补东西（文档、说明、配置模板等），照这页的最小流程走就行。不用背命令，知道每一步在干什么最重要。

## 先理解三个词

- **分支（branch）**：一条独立的修改线。在分支上怎么改，都不会弄坏主线；改好了再决定要不要合回去。
- **提交（commit）**：一次存档。每次提交写一句说明（改了什么），以后能查、能退。
- **推送（push）**：把本机的存档上传到 GitHub。推了，别人（和云端备份）才看得到。

还有一个词：**合并（merge）**——把一条分支的改动并进另一条。合并和发布都是大事，先想清楚再做。

## 五条规矩

1. **不在生产线分支上直接改**（`deploy/merged-20261102` 是正在运行的版本，更不要动上游基线 `main`）。每次改动先开一条新分支。
2. **一个分支只做一件事**，名字说清用途，例如 `docs/补一份说明`、`feat/加个小功能`。
3. **提交说明写人话**：一句说清「改了什么、为什么」，以后自己回头看得懂。
4. **推送前先扫一眼内容**：确认没有把密钥、令牌、密码、私人配置、运行数据（`~/.orbit` 里的东西）一起传上去。这些永远不进仓库。
5. **合并、发布、改项目名这类动作不顺手做**：单独决定，必要时先问 Muse 或 Dot。

## 最小操作流程（命令行版）

在仓库目录里依次执行（把尖括号里的内容换成实际的）：

```bash
# 0. 先看现在在哪、干不干净
git status
git branch

# 1. 从当前分支开一条新分支并切过去
git switch -c feat/<这次改动的名字>

# 2. 改文件（用任何编辑器都行）

# 3. 把改动加入本次提交
git add <文件名>
git status        # 再确认一遍要提交的就是这些

# 4. 提交，写清说明
git commit -m "一句话说明：改了什么、为什么"

# 5. 推到 GitHub（这条分支第一次推时用这一句）
git push -u origin feat/<这次改动的名字>
```

推完到 GitHub 网页上打开这条分支，确认文件都在、内容对。

## 想看看仓库现状时

```bash
git log --oneline -10     # 最近 10 次提交，一行一个
git branch -a             # 本地和远端的全部分支
git diff                  # 还没提交的改动
```

## 改坏了怎么退

- **还没提交**：`git restore <文件名>` 把这个文件恢复原样。
- **已经提交、还没推**：`git reset --soft HEAD~1` 退回上一个存档，改动还在文件里，可以改完重新提交。
- **已经推上去了**：不要强行改历史。用 `git revert <提交号>` 生成一个「反向提交」把改动抵消，历史完整、可查。
- **拿不准就停手**：把现状告诉 Muse，由它核对后再动——退错了比改错了更麻烦。

## 也可以不自己敲命令

把要补的内容（文档全文、要改的段落）交给 Muse，它会走这条通道代劳：

- Muse 的写入通道是 GitHub 连接器：**开分支＋一个快照提交**推送（提交的是文件最终内容的全量快照，不是逐条本地历史），推完逐个文件回读核对。
- 按现行规矩：推送前先做密钥/数据泄漏扫描，干净就直接推、推完报告；扫到可疑内容才停下来问。
- 合并与发布不在代劳范围内，仍单独决定。

## 常见问题

- **网页上看到的 README 和实际在用的对不上？** README 还是上游原文，现行状态看 `docs/FORK-STATUS.md`（本仓库的《fork 当前状态》）。
- **分支越攒越多怎么办？** 已合入生产线的分支可以留着作记录，不必急着删；拿不准的先不删。
- **两个人同时改了同一个文件怎么办？** 尽量避免：开工前互相通气（比如在信箱里说一声），同一文件同一时间只由一个人改。
